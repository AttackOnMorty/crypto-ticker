## Executive summary

Overall posture: **Stable** (first run — no trend yet)

A tidy ~600-line macOS menu-bar app. Security posture is genuinely good for a read-only public-data client. The dominant risks are concurrency and steady-state CPU: shared mutable state is read on a background WebSocket queue while written on main (data race), and the entire menu is rebuilt on every trade message. Both are fixable without architectural upheaval.

| Aspect | Verdict |
|--------|---------|
| Bugs | One Critical data race on shared WebSocket state; reconnect path leaks/duplicates sockets. |
| Performance | Full NSMenu rebuild + NumberFormatter alloc on every trade tick — CPU spin in steady state. |
| Security | Clean. Sandboxed, minimal entitlements, TLS-only, defensive JSON parsing, no secrets. Two Low hardening notes. |
| Maintainability | Dead code + theatrical `validate()`/`fatalError` + stringly-typed notifications violate the repo's YAGNI rule. |

## Top findings

> **How to read:** Severity 🔴 Critical · 🟠 High · 🟡 Medium · ⚪ Low. Effort: **Quick win** (<1h) · **Moderate** (hours) · **Large** (refactor). Lows folded into `baseline.json` are listed at the end of each aspect.

### Bugs

#### F1 · 🔴 Critical — WebSocket data arrives on a background thread but shares state with the UI without locking

**Status:** 🆕 new · **Effort:** Large

**Impact:** Under normal use (a trade arriving while the user opens the menu or toggles a coin) the app can read corrupted dictionary/array internals and crash with `EXC_BAD_ACCESS`, or silently mis-track which sockets are open.

**Fix:** Confine all access to the shared collections to one thread — make `WebSocketManager` a `@MainActor` type, or hop to the main queue at the very top of the receive handler before touching any shared state.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `urlSession` (init), `receiveMessage(for:)`, `connectWebSockets()`, `toggleCryptoSelection(_:)`

**Evidence:** `private let urlSession = URLSession(configuration: .default)` is created with **no `delegateQueue`**, so `task.receive { … }` completion runs on URLSession's private background queue. Inside that closure the code reads shared value-type collections off-main: `webSocketTasks[symbol]` (`receiveMessage` guard), `selectedSymbols.contains(symbol)` (lines ~140/157/169), `connectionStates[symbol]` (line ~144). Meanwhile the **main** thread writes the same collections: `toggleCryptoSelection` mutates `selectedSymbols`, `connectWebSocket` does `webSocketTasks[symbol] = task`, `updateConnectionState` writes `connectionStates`. The init `Task { … connectWebSockets() }` also writes `webSocketTasks` off-main at startup. Concurrent unsynchronized read+write of a Swift `Dictionary`/`Array` is a data race → heap corruption / crash. The `@Published` wrappers do not provide synchronization.

**Suggested fix:**

```swift
@MainActor
class WebSocketManager: ObservableObject { … }
// and in the receive closure:
task.receive { [weak self] result in
    Task { @MainActor in
        guard let self, self.selectedSymbols.contains(symbol) else { return }
        … // all shared-state access now on main
    }
}
```
</details>

#### F2 · 🟠 High — Reconnect overwrites the socket entry without cancelling the old one, leaking/duplicating connections

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** A dropped connection (sleep/wake, network blip) can leave a zombie socket running its own receive loop while a new one starts — duplicate price updates, leaked sockets, and connection state that no longer matches reality.

**Fix:** Before reconnecting, cancel and remove the existing task (call `disconnectWebSocket(for:)`), and guard the delayed reconnect with `webSocketTasks[symbol] == nil` so it doesn't clobber a socket established in the meantime.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `receiveMessage(for:)` `.failure` branch → `connectWebSocket(for:)`

**Evidence:** On `.failure` the code schedules `connectWebSocket(for: symbol)` after `reconnectDelay`. `connectWebSocket` does **not** cancel/remove the prior task — it overwrites `webSocketTasks[symbol] = task`. The failed task is never `cancel()`ed (leaked) and is left in the dict until the delayed closure fires. The delayed reconnect checks only `selectedSymbols.contains(symbol)`, not whether a task already exists, so if the user toggled the coil off→on (or `connectWebSockets()` ran) in the 5s window, a live socket gets orphaned and its receive loop keeps running against a dropped reference.

**Suggested fix:**

```swift
DispatchQueue.main.asyncAfter(deadline: .now() + reconnectDelay) {
    guard self.selectedSymbols.contains(symbol),
          self.webSocketTasks[symbol] == nil else { return }
    self.connectWebSocket(for: symbol)
}
// and have the failure branch remove+cancel the failed task first.
```
</details>

#### F3 · 🟡 Medium — A failed socket stays in the task map, so reconnection logic thinks it's still connected

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** After a failure, `connectWebSockets()` sees the stale entry and skips reconnecting that symbol; the status bar can show a stale price with a ⚠️ indicator indefinitely.

**Fix:** Remove the task from `webSocketTasks` in the failure branch (tie this to F2's fix), so the diff logic correctly treats the symbol as needing a fresh connection.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `connectWebSockets()` diff (`webSocketTasks[symbol] == nil`) vs `receiveMessage` failure branch

**Evidence:** `connectWebSockets()` connects only symbols where `webSocketTasks[symbol] == nil`. A failed task is never removed before its delayed reconnect, so a concurrent `connectWebSockets()` treats the symbol as live and skips it — `connectionStates` and the real socket diverge.
</details>

#### F4 · 🟡 Medium — A cancelled socket's in-flight callback overwrites the just-set "disconnected" state with "error"

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** Toggling a coin off can briefly flash an error state instead of disconnected and fires a redundant full menu rebuild.

**Fix:** Guard the `.failure` branch on `webSocketTasks[symbol] != nil` (or that the symbol is still selected) before updating state, so a deliberate cancel doesn't masquerade as an error.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `disconnectWebSocket(for:)` vs `receiveMessage(for:)` `.failure`

**Evidence:** `disconnectWebSocket` cancels the task and sets `.disconnected`, but an already-queued `receive` completion then fires `.failure` → `updateConnectionState(.error(...))`, which has no selected-symbol guard and clobbers `.disconnected`, posting an extra `ConnectionStateChanged`.
</details>

#### F5 · 🟡 Medium — The menu is rebuilt and reassigned while the user has it open

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** `menuWillOpen` kicks off REST fetches whose completions reassign `statusBarItem.menu` while the menu is visible, which can flicker or drop the user's interaction.

**Fix:** Don't replace `statusBarItem.menu` while the menu is open — update item titles in place, or only rebuild on `menuDidClose` / via a throttled path.

<details><summary>Technical details</summary>

**Where:** `AppDelegate.swift` — `updateMenu()` driven by `PriceUpdated`, plus `menuWillOpen(_:)` → `fetchAllCryptoPrices()`

**Evidence:** `updateMenu` does `self.statusBarItem.menu = self.createMenu()`. `menuWillOpen` triggers 7 REST fetches, each completion posts `PriceUpdated` → `updateMenu` reassigns the whole menu while it's on screen. (Shares a root cause with F6.)
</details>

_Also tracked in `baseline.json` (Low): `timer-never-invalidated`, `percent-double-format-roundtrip`, `formatprice-rounds-large-to-whole-dollar`._

### Performance

#### F6 · 🔴 Critical — The entire menu is torn down and rebuilt on every single trade message

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** A hot symbol like BTC streams tens of trades/sec; each one rebuilds all 7 menu items + 7 `NSAttributedString`s and reassigns the menu on the main thread — continuous CPU churn even when the menu is closed and the user sees nothing.

**Fix:** Decouple data updates from menu rebuilds: the status-bar title already refreshes on its own 1Hz timer, so only build menu items when the menu is about to open (or throttle rebuilds to ~1Hz).

<details><summary>Technical details</summary>

**Where:** `AppDelegate.swift` — `updateMenu()` observing `PriceUpdated` + `ConnectionStateChanged`; `WebSocketManager.handleIncomingData` posts `PriceUpdated` per trade

**Evidence:** `handleIncomingData` → `NotificationCenter.post("PriceUpdated")` on every `@trade` message → `updateMenu()` → `createMenu()` loops all 7 `availableCurrencies` building attributed strings + NSFont lookups, then `statusBarItem.menu = …`. The UI need is ~1Hz (already covered by the Timer); the per-message rebuild is wasted work.

**Suggested fix:**

```swift
// Build menu items lazily in menuNeedsUpdate(_:)/menuWillOpen, not on every PriceUpdated.
// Drop the PriceUpdated→updateMenu wiring; keep the 1Hz status-bar title refresh.
```
</details>

#### F7 · 🟠 High — A new NumberFormatter is allocated on every price format call

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** `NumberFormatter()` creation (locale + ICU setup) is among the most expensive Foundation operations, and it runs on the hottest path — once per trade message per active symbol.

**Fix:** Create the formatters once (static/lazy) and reuse them; only `maximumFractionDigits` varies.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `formatPrice(_:)`, `formatPercent(_:)`

**Evidence:** Both functions do `let formatter = NumberFormatter()` then configure and discard it every call. `formatPrice` is called from `handleIncomingData` on every trade.

**Suggested fix:**

```swift
private static let priceFormatter: NumberFormatter = {
    let f = NumberFormatter(); f.numberStyle = .decimal; f.usesGroupingSeparator = true; return f
}()
// reuse, set maximumFractionDigits per call
```
</details>

#### F8 · 🟠 High — Opening the menu refetches all 7 coins over REST every time, even unselected ones

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** A user tracking only BTC issues 7 REST calls per menu-open (6 wasted), each firing a `PriceUpdated` → full rebuild (F6) at the worst possible moment — right as the menu appears.

**Fix:** Fetch only on a cache miss / staleness, or only for selected symbols; debounce rapid opens.

<details><summary>Technical details</summary>

**Where:** `AppDelegate.swift` — `menuWillOpen(_:)`; `WebSocketManager.fetchAllCryptoPrices()`

**Evidence:** `menuWillOpen` calls `fetchAllCryptoPrices()` which `withTaskGroup` fans out 7 `…/ticker/24hr` requests unconditionally on every open, with no caching/debounce.
</details>

#### F9 · 🟡 Medium — The 1-second status-bar timer fires forever, even with nothing to show

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** Prevents the app from ever idling; wakes the main thread every second and reassigns `button.title` even when text is unchanged or no symbols are selected.

**Fix:** Skip the work when `selectedSymbols` is empty or the computed string is unchanged; consider invalidating the timer when idle.

<details><summary>Technical details</summary>

**Where:** `AppDelegate.swift` — `startPriceUpdates()`, `updateStatusBarTitle()`

**Evidence:** `Timer.scheduledTimer(withTimeInterval: 1.0, repeats: true)` always dispatches to main and sets `button.title` each tick regardless of change.
</details>

#### F10 · 🟡 Medium — All 7 coins are fetched at launch when only the selected subset is shown

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** 6 extra cold-start REST requests (default selection is just BTC), each posting `PriceUpdated` → rebuild (F6) during launch.

**Fix:** At init, fetch only `selectedSymbols`; fetch the rest lazily when the menu first opens.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `init()` → `fetchAllCryptoPrices()`

**Evidence:** `init` awaits `fetchAllCryptoPrices()` (all 7) before `connectWebSockets()`, though only the selected symbol(s) appear in the bar.
</details>

### Security

> Sandbox & entitlements, transport (TLS/WSS, no ATS exceptions), untrusted-JSON crash safety, logging, and secrets were all reviewed and are **clean**. The two items below are defense-in-depth hardening, not exploitable vulnerabilities.

#### F11 · ⚪ Low — Unparseable feed values are rendered verbatim in the UI

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** A compromised/MITM'd feed (hard, given TLS to Binance) could push arbitrary text into the menu/status-bar title — UI spoofing only, no code execution (native AppKit text, no HTML/JS).

**Fix:** When `Double(price)` fails, show a placeholder (e.g. `—`) instead of the raw remote string.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` `formatPrice` (`guard let … else { return price }`) → `AppDelegate.swift` `createAttributedTitle`

**Evidence:** `formatPrice` returns the raw string on parse failure; it flows into `"… $\(price) …"` unsanitized. No crash path (no force-unwrap).
</details>

#### F12 · ⚪ Low — Symbols loaded from UserDefaults aren't validated against the known coin list

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** An attacker who can already write the sandboxed plist (i.e. has local file access) could inject a path/query segment into the request URL. Scheme/host/port are hardcoded and `URL(string:)` rejects illegal chars, so the host can't be redirected — low real-world risk.

**Fix:** Intersect loaded `selectedSymbols` with `availableCurrencies` symbols on load.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `loadSelectedCryptos()`, `connectWebSocket(for:)`, `fetchPrice(for:)`

**Evidence:** `selectedSymbols = UserDefaults… as? [String] ?? defaults` with no allowlist check; each symbol is interpolated into the WSS/REST URL.
</details>

### Maintainability

> Judged against the repo's own YAGNI rule (global CLAUDE.md): no speculative abstraction, configuration, or extensibility without a current need.

#### F13 · 🟠 High — Dead code: an unused view, two unused error cases, three unused config constants, an empty scene

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** Readers repeatedly investigate inert symbols to confirm they do nothing; pure maintenance tax, directly against YAGNI.

**Fix:** Delete `ContentView.swift`, the `Settings { EmptyView() }` scene, the two unconstructed `WebSocketError` cases, and the unread `appName`/`version`/`bundleIdentifier`.

<details><summary>Technical details</summary>

**Where:** `ContentView.swift` (whole file); `WebSocketManager.swift` (`WebSocketError.connectionFailed`, `.dataParsingFailed`); `AppConfiguration.swift` (`appName`, `version`, `bundleIdentifier`); `CryptoTickerApp.swift` (`Settings` scene)

**Evidence:** grep confirms zero references outside the declaration sites. `WebSocketError` constructs only `.invalidURL` and `.networkError`. `ContentView` is template scaffolding returning `EmptyView()` with no consumer.
</details>

#### F14 · 🟠 High — `validate()` + `fatalError` guards against inputs that can't exist

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** Implies config is dynamic/external when it's all hardcoded literals; the `fatalError` is unreachable — a loaded gun pointed at a wall, and speculative flexibility YAGNI forbids.

**Fix:** Delete `validate()` and the `fatalError` in `CryptoTickerApp.init()`.

<details><summary>Technical details</summary>

**Where:** `AppConfiguration.validate()`; `CryptoTickerApp.init()`

**Evidence:** `validate()` null-checks `URL(string:)` of two hardcoded valid literal URLs and `statusBarUpdateInterval > 0` against a hardcoded `1.0`. The guard can never fail at runtime.
</details>

#### F15 · 🟠 High — Notification names are raw string literals duplicated across files

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** A typo in any of the 5 literals silently breaks the publish/subscribe link with no compiler error; the `userInfo` payload posted with `ConnectionStateChanged` is never read.

**Fix:** Define `static let` notification names in one place and reference them; drop the unused `userInfo`.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` (posts `"PriceUpdated"`, `"ConnectionStateChanged"`) and `AppDelegate.swift` (observers)

**Evidence:** `NSNotification.Name("PriceUpdated")` and `"ConnectionStateChanged"` appear as raw literals in 5 places across 2 files. `updateMenu` takes no notification arg and ignores the posted `userInfo: ["symbol":…, "state":…]`.
</details>

#### F16 · 🟡 Medium — Percent value is parsed and formatted in two divergent places, round-tripping String→Double→String→Double→String

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** Changing the percent display format requires edits in two files with two different mechanisms — a divergence trap.

**Fix:** Format the percent once (single helper), store the numeric value (not a pre-formatted string), and format only at display time.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.formatPercent` (NumberFormatter, appends `"%"` at call site) vs `AppDelegate.formatPriceChange` (`String(format:"%+.2f%%")`); the strip-and-parse `Double(change.replacingOccurrences…)` is copy-pasted twice in `createAttributedTitle`. `"Loading..."` literal duplicated too.

**Evidence:** Manager formats + appends `%`, stores the string; delegate strips `%`/`+`, re-parses, re-formats.
</details>

#### F17 · 🟡 Medium — `ObservableObject`/`@Published` is never observed; three overlapping update mechanisms coexist

**Status:** 🆕 new · **Effort:** Moderate

**Impact:** Misleading architecture — a reader assumes SwiftUI reactive bindings exist; the actual refresh trigger (notifications + 1Hz timer + unused @Published) is ambiguous when debugging staleness.

**Fix:** Drop `ObservableObject`/`@Published` (no SwiftUI consumer), and consolidate on a single update path (see F6).

<details><summary>Technical details</summary>

**Where:** `WebSocketManager` (`ObservableObject` + 4 `@Published`) vs `AppDelegate` (NotificationCenter + Timer)

**Evidence:** The only consumer is AppKit via `NotificationCenter` and a polling `Timer`; no SwiftUI view observes the object (`ContentView` dead, `Settings` empty). The `@Published` wrappers are inert.
</details>

## Action plan (execution order)

No unit-test harness exists, so every item is **run-verify** (confirmed by running the app and observing the menu bar). Order is by safety + file overlap, not severity alone. Recommend adding a minimal test target for the format/diff helpers before the F1 refactor.

1. **Phase 1 — isolated quick wins (low risk, bank them first):**
   - F13 delete dead code · F14 delete `validate()`/`fatalError` · F15 notification-name constants · F7 shared formatters · F9 idle-skip timer · F10 fetch only selected at init · F11 placeholder for unparseable price · F12 validate symbols against allowlist.
2. **Phase 2 — behavioral fixes in the WebSocket/menu hot paths (before restructuring them):**
   - F4 guard failure branch · F3 remove failed task from map · F2 cancel-before-reconnect + existence guard · F8 fetch-on-staleness for menu open · F5 stop reassigning menu while open.
3. **Phase 3 — structural changes, isolated, verify after each:**

### Bugs

#### F1 · 🟠 High — A silently-dropped connection (sleep/wake, dead wifi) can leave prices frozen with no recovery

**Status:** 🆕 new (pre-existing, newly identified) · **Effort:** Moderate

**Impact:** Directly answers "will it idle over days?" — if the TCP connection half-opens (no FIN/RST, common on laptop sleep/wake or NAT timeout), `receive` never completes with `.failure`, so reconnect never fires. The socket stays `.connected`, the status bar shows a stale price with a green dot, and it never recovers until the app restarts.

**Fix:** Add a liveness mechanism — schedule `task.sendPing` periodically and/or a staleness watchdog that forces a reconnect if no message has arrived in N seconds.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `receiveMessage` / `handleReceive` / `scheduleReconnect`

**Evidence:** Reconnection is driven *only* by `handleReceive(.failure)`. There is no `sendPing`, no read timeout, and no idle watchdog. A clean server close self-heals (the next `receive` re-arm fails), but a half-open connection delivers neither data nor error, so `handleReceive` is never called and `scheduleReconnect` never runs. Binance also force-closes any stream at 24h; that normally surfaces as `.failure`, but there is no defense if it ever doesn't. **This is the run-verify item:** with the app running, toggle wifi off→on — if ⚠️ doesn't clear within ~5s, this gap is live.
</details>

#### F2 · 🟡 Medium — Reconnect retries forever every 5s with no backoff or cap

**Status:** 🆕 new (pre-existing) · **Effort:** Quick win

**Impact:** During a sustained outage (hotel wifi, long sleep), each selected symbol retries on a fixed 5s cadence indefinitely — perpetual `logger.error` + `Task`/URL allocation, battery/network drain over hours, no ceiling.

**Fix:** Exponential backoff with a max interval (e.g. 5s → 60s) and optionally a retry cap; this also bounds the log volume.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `scheduleReconnect`

**Evidence:** `Task { @MainActor in try? await Task.sleep(5s); guard shouldReconnect; connectWebSocket }`. Fixed delay, no backoff, no cap. Can't stack (one in-flight task per symbol via the `shouldReconnect` guard), so no tight spin — but unbounded fixed-rate retry.
</details>

#### Low (bugs) — quick list

- ⚪ **`attributed-title-miscolor-placeholder`** (`AppDelegate.attributedMenuTitle`) — refactor side-effect of the `—` placeholder: `fullText.range(of: changeText)` colours the *first* `—`; if a malformed feed makes `price` format to `—` *and* `change` is `—`, the change colour lands on the price token. Narrow trigger (needs non-numeric price over TLS). Fix: colour the change by an explicit suffix range, not `range(of:)`.
- ⚪ **`rest-uses-shared-session`** (`WebSocketManager.fetchPrice`) — REST uses `URLSession.shared` while sockets use the stored `urlSession`; pre-existing inconsistency, harmless today. (Also Maint.)
- ⚪ **`reconnect-task-strong-self`** (`scheduleReconnect`) — `Task` captures `self` strongly; pins the manager for ≤5s. No real leak (app-lifetime owner).
- ⚪ **`stale-24h-percent-while-open`** (`handleIncomingData`/`configureMenuItem`) — `priceChanges` only refreshed by REST (debounced 10s, checked only at `menuWillOpen`), so a menu held open shows a live price next to a frozen %. Internally consistent, likely intended.

### Performance

#### F7 · 🟡 Medium — `.priceUpdated` is posted on every trade even though its only observer no-ops while the menu is closed

**Status:** 🆕 new (refactor side-effect) · **Effort:** Quick win

**Impact:** A consequence of the F6 decoupling: the sole observer (`dataDidChange`) returns immediately unless the menu is open (≈always closed for a menu-bar app), yet `handleIncomingData` still posts on every `@trade` (tens–hundreds/sec aggregate). The status bar is driven by the 1Hz timer, so the post does nothing useful while closed — pure main-actor dispatch overhead, forever.

**Fix:** Gate the post on "menu open" (expose the flag to the manager, or skip the notification and let the menu pull on open).

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.handleIncomingData` (posts `.priceUpdated`) → `AppDelegate.dataDidChange` (`guard menuIsOpen else { return }`). Grep confirms exactly one observer.
</details>

#### F8 · 🟡 Medium — Full JSON dictionary allocated per trade to read a single field

**Status:** 🆕 new (pre-existing, now on the main actor) · **Effort:** Quick win

**Impact:** Each `@trade` message does `text.data(...)` + `JSONSerialization.jsonObject` parsing all ~9 keys into a boxed `NSDictionary`, then reads only `["p"]`. Because the manager is `@MainActor`, this allocation now runs on the main thread on the hottest path — steady churn over a long-running session.

**Fix:** Decode only the price field (small targeted parse / `Codable` struct with just `p`), or hop the parse off the main actor before assigning.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.handleIncomingData`. Payload tiny so no single-frame jank, but sustained 50–200 parses/sec allocate and free continuously on main.
</details>

#### Low (perf) — quick list

- ⚪ **`redundant-refresh-on-fetch-fanout`** (`fetchPrice` posts per symbol) — one on-open fetch fires up to 7 `.priceUpdated` posts → 7 full `refreshMenuItems` passes (≈49 attributed-string builds) plus the explicit refresh, where one coalesced refresh would do. Bounded to menu-open, ≤ every 10s.
- ⚪ **`timer-builds-string-each-tick`** (`updateStatusBarTitle`) — builds `createStatusBarDisplayText()` every second *before* the idle-skip compare, so the string is allocated then often discarded. Microsecond-scale; the costly UI write is already gated.

### Maintainability

All new helpers (`PriceFormatter`, `WebSocketPlan`, `StatusBarText`, `validSymbols`, `menuFetchDebounce`) are used in production — **no test-only production code**. Three Low items:

- ⚪ **`prices-changes-asymmetry-undoc`** (`WebSocketManager` properties) — `prices` stores formatted strings, `priceChanges` stores raw; correct and deliberate (keeps `percentValue` round-trip-free) but uncommented, so a future "consistency fix" could silently break the colour logic. Add a one-line comment.
- ⚪ **`placeholder-inconsistency`** — three "no data" representations coexist: `PriceFormatter.placeholder = "—"`, menu price default `"Loading..."`, change default `""`. Consolidate.
- ⚪ **`websocketmanager-file-grab-bag`** — `WebSocketManager.swift` holds 6 top-level concerns (notification names, 2 enums, `CryptoCurrency`, 3 pure helpers, the class); `StatusBarText` is used only by `AppDelegate`. Note: the project uses **synchronized file groups** (objectVersion 77), so new files *are* auto-included in the Xcode target — splitting these out is now safe (no pbxproj edit), unlike assumed during the fix pass.

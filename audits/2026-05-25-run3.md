### Bugs

#### F1 · 🟠 High — A stale keepalive-ping failure can tear down a healthy reconnected socket

**Status:** 🆕 new (regression from run2 F1) · **Effort:** Quick win

**Impact:** Occasionally drops a *working* connection: a coin briefly shows ⚠️ and reconnects (~5s) for no real reason. Self-heals, but it's wrong behavior caused by the keepalive that was meant to improve reliability.

**Fix:** Capture the pinged task in the `sendPing` closure and only tear down if it's still the current socket (`webSocketTasks[symbol] === pingedTask`). Best done by routing both failure paths through one helper that takes the specific task (see F4).

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `pingActiveSockets` / `handlePingFailure`

**Evidence:** `pingActiveSockets` captures only `symbol` (a String) in the `sendPing` completion. Sequence: socket A is pinged → A fails and is replaced by a healthy new socket B (reconnect) → A's ping-failure completion arrives and runs `handlePingFailure(for: "…")`. The guard checks only `webSocketTasks[symbol] != nil` — true, but it's now **B** — so it cancels B, sets `.error`, and schedules another reconnect. The 30s ping interval overlaps the ≥5s backoff window, so a reconnect completing within a ping's flight time is reachable.
</details>

#### F2 · 🟡 Medium — Concurrent ping-failure and receive-failure double-schedule a reconnect

**Status:** 🆕 new (regression from run2 F1/F2) · **Effort:** Quick win

**Impact:** When a socket dies, both its receive `.failure` and a pending ping failure can fire. `reconnectAttempts` is incremented twice and two reconnect Tasks are scheduled, inflating the backoff faster than intended. No duplicate live socket (the `shouldReconnect` guard prevents that), but the backoff accounting is wrong.

**Fix:** Same helper as F1 — `handleReceive(.failure)` lacks the task-presence/identity guard that `handlePingFailure` has; route both through one guarded path so only the first failure for a given task acts.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `handleReceive(.failure)` vs `handlePingFailure`

**Evidence:** If `handlePingFailure` runs first it removes the task and schedules a reconnect; then `handleReceive(.failure)` runs with no presence guard, calls `removeValue` (no-op), `updateConnectionState(.error)`, and `scheduleReconnect` again → double increment of `reconnectAttempts`.
</details>

### Performance

#### F3 · ⚪ Low — `TradeMessage` decode comment overstates the performance win

**Status:** 🆕 new · **Effort:** Quick win (doc)

**Impact:** Misleading comment, not a runtime problem. `JSONDecoder.decode` still does a full JSON parse plus a `Data` copy per trade, so the cost is comparable to the old `JSONSerialization` path — not cheaper. The real benefit was type-safety / dropping the `as? [String:Any]` cast, not parse cost.

**Fix:** Correct the comment to claim type-safety/clarity rather than a parse-cost reduction (keep `TradeMessage` — it's cleaner). A genuinely cheaper path (manual `"p":"…"` scan) isn't worth the fragility at ~10 msg/sec.

<details><summary>Technical details</summary>

**Where:** `WebSocketManager.swift` — `TradeMessage` doc comment + `text.data(using:.utf8)` per message.
</details>

### Maintainability

#### F4 · ⚪ Low — Failure teardown duplicated across two sites (root cause of F1/F2)

**Status:** 🆕 new · **Effort:** Quick win

**Impact:** `handleReceive(.failure)` and `handlePingFailure` independently do log → drop task → set `.error` → `scheduleReconnect`, with subtly different guards (only the ping path checks presence). The duplication is *why* the guards drifted and the identity race exists.

**Fix:** Extract `handleConnectionFailure(for:task:error:cancelTask:)` that checks task identity once and runs the teardown/reconnect; call it from both sites. Resolves F1 and F2 too.
